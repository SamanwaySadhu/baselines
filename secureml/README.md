# Baseline 5: SecureML (secret sharing + Beaver triples), made maliciously secure

This baseline trains logistic regression with the protocol of **SecureML** (Mohassel & Zhang, S&P 2017): the data and
the weights are additively secret-shared between two parties, the matrix products use Beaver triples in *matrix form*
generated by OT, and the activation is SecureML's piecewise function. The paper's protocol is semi-honest. This
implementation adds **malicious security** (security with abort against an active adversary that corrupts either
party): SPDZ/MASCOT-style information-theoretic MACs on every share, OT-based authenticated preprocessing with a
sacrifice check, and a batched MAC check before any output is accepted. `--semi-honest` switches all of that off, so
the cost of malicious security can be measured on the same code.

| role | holds | learns |
|---|---|---|
| **client** (party 0) | every private input: the training data (x, y) and the initial weights w0 (random for now) | nothing |
| **server** (party 1) | no input | the trained weights, and only if every check passed |

The client and the server play the two non-colluding SecureML "servers". The client is also the data owner, so
instead of sending shares of its data to a second server it sends the *masked* data `E = X - U` (the SecureML trick: the
random mask `U` is shared, and `E` is revealed once for the whole training). The server never sees the data, the labels
or w0. Neither party sees an intermediate weight or sigmoid value: everything it receives is uniformly random.

Training defaults match the sibling baselines: **20 iterations, batch 4, learning rate 0.5**, `d` features including
the bias column (`--d`). The client's random data and initial weights are generated exactly like in the other
baselines (same `--seed` gives the same values), then shifted to the fixed-point scale of this protocol.

## What is computed

All numbers are integers in the prime field F_p, p = 2^127 - 1 (a value `v` at *scale s* stands for `v / 2^s`).
F = `--frac` (default 13), `k = log2(batch / lr)` (3 for lr 0.5, batch 4).

| quantity | scale |
|---|---|
| features x, labels y, sigmoid output ŷ, error e = ŷ − y | F |
| weights w | S_w = 2F + k |
| z = Σ_j x_j w_j (exact, nothing is truncated) | 3F + k |
| gradient g_j = Σ_i e_i x_ij | 2F |

Per iteration, on a batch of rows `i`:

```
z_i  = sum_j x_ij w_j                                       Beaver, matrix form
ŷ_i  = clamp( floor((z_i + 1/2) / 2^(2F+k)), 0, 2^F )       SecureML's activation (eq. 4), exact
e_i  = ŷ_i − y_i
g_j  = sum_i e_i x_ij                                       Beaver, matrix form
w_j  = w_j − g_j                                            lr/batch = 2^-k is folded into the scale of w
```

Because `S_w = 2F + k`, the update needs no truncation at all, and the dot products are exact. The only rounding in
the protocol is the floor in the activation, which is computed **exactly**. The result of a run therefore equals the
plaintext integer reference (`reference_train` in `include/params.h`) **bit for bit**. `--verify` (server, test only)
and `lr_secureml_selftest` check this; `--verify` also prints the distance to unquantized double-precision SGD with the
same activation (about 1e-4 at the defaults).

As in SecureML the backward pass uses the logistic-regression gradient `(f(z) − y) x`, not the derivative of the
piecewise function.

## Protocol

Notation: `[x]` is an authenticated share (below), `d`, `B`, `T` = features, batch, iterations, `n = T·B` samples.

### Offline phase (data independent)

1. **Masks.** The client draws `U` (one random field element per data entry), `Rw` (masks w0), `Ry` (masks the labels);
   the server draws `Rout` (masks the output). The shared random vectors `Vf_t` (masks w in the forward pass) and `Vb_t`
   (masks e in the backward pass) are sums of one random share per party.
2. **Matrix triples by OT** (SecureML Sec. 4.2). Per iteration `Zf_t = U_t · Vf_t` (B×d times d) and
   `Zb_t = U_tᵀ · Vb_t` (d×B times B). `U` is known to the client, so `U·(V_0 + V_1) = U·V_0` (local) `+ U·V_1`, and
   the only cross term is **one OT product** with the client as message sender and the server choosing with the bits of
   `V_1`. The product is vectorized as in the paper: all entries multiplied by the same bit of `V_1[j]` (a column of
   `U`) share one set of 127 OTs, expanded with AES counter mode. The scalar triples `(a, b, c = ab)` for the activation
   need two OT products each (one per direction).
3. **Authentication.** Every shared value gets a MAC share (`α · x`, α = α_0 + α_1) by one OT product with the *other*
   party's key bits as the choice bits (two for values both parties share, one for client-known masks).
4. **Sacrifice** (malicious only). Every triple is generated with a partner `(Uh, Zh = Uh·V)` that shares `V`. After a
   coin toss for `ρ`, `ρ·U − Uh` is opened and `ρ·Z − Zh − (ρ·U − Uh)·V` must open to 0, for the matrix triples and for
   every scalar triple. A party that fed inconsistent inputs into an OT product is caught except with probability 2^-127.
5. **Random bits.** `[a]` random, open `s = a²` (one Beaver multiplication), `bit = (a/√s + 1)/2`. That is a bit
   exactly when the opening of `s` is right, and openings are MAC-checked. `N + ssp` bits are consumed per activation.
6. **MAC check** of everything opened so far.

### Online phase

* **Input** (1 flight): the client sends `E = X − U`, `w0 − Rw` and `y − Ry` (all uniformly random to the server).
* **Per iteration** (11 round trips):

| step | exchanges |
|---|---|
| open `F = w − Vf_t` | 1 |
| `z_i = Zf_i + Σ_j F_j [U_ij] + Σ_j E_ij [Vf_j] + Σ_j E_ij F_j` (local) | 0 |
| activation, masked opening `c = z + 1/2 + 2^(N−1) + r` with `N + ssp` random bits `r` | 1 |
| three borrow chains as log-depth trees of Beaver products (`⌈log2(N−1)⌉` = 6 levels) | 6 |
| the two xor products, then `ŷ = g2·2^F + (g1 − g2)·q` | 2 |
| open `F' = e − Vb_t` | 1 |
| `g_j = Zb_j + Σ_i F'_i [U_ij] + Σ_i E_ij [Vb_i] + Σ_i E_ij F'_i`, `w_j −= g_j` (local) | 0 |

* **Output**: open `w + Rout` (so only the server, who knows `Rout`, learns `w`), then the final **MAC check**, then the
  server accepts. Nothing is accepted before every opened value of the run has been verified.

### The activation, exactly

With `v = z + 1/2` at scale `3F + k`, `T = 2F + k`: the result is `clamp(⌊v / 2^T⌋, 0, 2^F)`. One masked opening
`c = v + 2^(N−1) + r` (`r` = `N + ssp` random shared bits, `|v| < 2^(N−2)`, so the top `ssp` bits hide `v`
statistically) gives everything:

```
q  = ⌊v / 2^T⌋ = ⌊c / 2^T⌋ − 2^(N−1−T) − Σ_{i≥T} 2^(i−T) r_i − [c mod 2^T < r mod 2^T]
g1 = [v ≥ 0]   = c_{N−1} ⊕ r_{N−1} ⊕ [c mod 2^(N−1) < r mod 2^(N−1)]
g2 = [q ≥ 2^F] = the same with c replaced by c − 2^(3F+k)
ŷ  = g2·2^F + (g1 − g2)·q
```

`[public < secret bits]` is a borrow chain, evaluated as a tree: `(G, P)` segments combine to
`(G_hi + P_hi·G_lo, P_hi·P_lo)`. The number of multiplications per activation, `chain(T) + 2·chain(N−1) + 3`, is
data independent, so the triple schedule is fixed (`lr_secureml_selftest` checks that the triple pool is consumed
exactly). `N = 3F + k + ⌈log2(d·w_max + 2)⌉ + 2` where `w_max = 1 + iters·batch/2^k` bounds the weights; the
program refuses parameters for which `N + ssp` does not fit the field.

## Malicious security

**Model.** A static, active adversary corrupts the client *or* the server. The protocol is secure with abort: a
deviation is detected and both parties stop, and the server outputs nothing unless all checks passed.

| deviation | caught by |
|---|---|
| wrong value in any opening (Beaver masks, `F`, `F'`, `c`, `w + Rout`, ...) | MAC check (every opened value is verified in a batch with fresh joint coefficients; error 2^-127) |
| wrong MAC share, or a chooser that uses other bits than its key `α` | MAC check |
| inconsistent inputs in an OT product (sender messages or chooser bits), wrong cross terms | sacrifice check (matrix and scalar triples) |
| inconsistent OT-extension setup or messages | SoftSpoken's maliciously secure mode (CSW base OT + consistency check) |
| cheating in the coin tosses and in the MAC check itself | commit-then-open, with the committer's identity hashed in |
| a non-bit "random bit" | `s = a²` is opened and MAC-checked |

`lr_secureml_selftest` injects seven kinds of deviations at either party (wrong opening in the offline and online
phase, bad scalar triple, bad matrix triple, inconsistent OT input, wrong MAC share, wrong check value) and requires
both parties to abort with no output; `scripts/test_tamper.sh` does the same with the real two-process binary
(`--tamper KIND --cheater client|server`).

**What this does and does not claim.**
- This is the standard SPDZ/MASCOT construction applied to SecureML's computation. There is **no formal proof for this
  code and no third-party audit**; the OT extension is emp-ot's SoftSpoken in its malicious mode, and the checks above
  were validated only by the tests listed.
- Like all dishonest-majority SPDZ-style protocols, a corrupted sender in an OT product can make the MAC check pass or
  fail depending on a bit of the other party's MAC key; since a failed check ends the run, this leaks at most one bit of
  `α` per execution, which only lowers the 127-bit soundness by one bit.
- There is no fairness: a malicious party can abort at any point. The server receives the masked output (`w + Rout`)
  before the final MAC check and uses it only if the check passes; a malicious client can still make the server abort.
- The protocol does not prove that the client's inputs are in range. The activation gadget assumes `|z| < d·w_max` for
  inputs in `[−1, 1]`. A client that feeds larger values can only corrupt (or randomize) the weights the server obtains;
  it cannot learn anything about them or about the server.

## Differences from the SecureML paper

| paper | here | why |
|---|---|---|
| ring Z_{2^64} | prime field F_{2^127−1} | MACs need a large field (sound check, and a 40-bit statistical mask on a 60-bit value); the Mersenne prime keeps arithmetic fast |
| local truncation of shares (result off by ±1 ulp, fails with small probability) | no truncation of products (scales are chosen so that the update is exact); one **exact** floor in the activation | share truncation cannot be combined with MACs |
| activation by garbled circuit + OT, with share switching | the same function by bit decomposition with authenticated shared bits | a maliciously secure garbled circuit would need authenticated garbling and a malicious-secure share conversion |
| offline phase by LHE or OT, client-aided variant | OT only (SoftSpoken, vectorized as in Sec. 4.2) | the client-aided variant weakens the security model; LHE is slower |
| two servers share data supplied by many clients | the client is one of the two servers and the data owner | it is the setting of the other baselines: the server has no input and learns only the weights |
| semi-honest | malicious; `--semi-honest` is the same arithmetic protocol without MACs, partners, checks and OT consistency checks | measuring the cost of malicious security |

`--semi-honest` is therefore the *same protocol family* without authentication, **not** a bit-for-bit reproduction of the
paper's garbled-circuit activation.

## Install and run (WSL / Linux)

The baseline needs only emp-tool and emp-ot (the same pinned versions as `../gc_ag2pc`; install them with
`../gc_ag2pc/scripts/install_emp.sh`, default prefix `$HOME/emp`), CMake >= 3.21, a C++20 compiler and OpenSSL 3.

```bash
cd baselines/secureml
EMP_PREFIX=$HOME/emp bash scripts/build.sh

./build/lr_secureml_selftest --quick     # field, OT products, MAC check, activation branches (under a second)
./build/lr_secureml_selftest             # + end-to-end vs the reference and all deviations (about 10 s)

bash scripts/run_local.sh --d 5          # both parties on this machine; the server prints the report
bash scripts/run_local.sh --d 1000 --semi-honest
bash scripts/test_tamper.sh --d 5        # real binaries: every deviation must abort
D_LIST="5 50 500" REPS=3 bash scripts/bench_sweep.sh     # results/sweep.csv
```

By hand, in two terminals or on two machines:

```bash
./build/lr_secureml server --port 12345 --d 100
./build/lr_secureml client --host <server-ip> --port 12345 --d 100
```

Options (`--help`): `--d --iters --batch --frac --lr --seed --no-bias --zero-init --qbits`; `--threads N`;
`--semi-honest`; `--ssp`; `--verify` (test only, the server regenerates the client's data from `--seed`); `--json FILE`,
`--csv FILE`, `--quiet`; `--tamper KIND --cheater client|server` (test only). Both parties must pass the same training
flags. The protocol uses TCP ports `port .. port + threads` (one main channel plus one OT channel per worker).

**All CPU cores.** `--threads` defaults to all hardware threads and sets, per party, the number of worker threads
*and* of OT connections. Every OT product is split across the workers (by items, or by columns when there are few
items), each with its own SoftSpoken sessions and socket; the local matrix work of the online phase is split across the
same threads for large `d`. If the parties use different `--threads`, both use the smaller one. When both run on the
same machine, give each half of the cores (`run_local.sh` and `bench_sweep.sh` do): otherwise they compete for the same
cores and the run gets slower.

## Cost report

Each party measures itself in contiguous phases named `stage/sub-phase` and the two tables are exchanged, so the server
prints both.

| stage | phases |
|---|---|
| **setup** | `handshake`; `ot_base` (base OTs and OT-extension bootstrap of every worker, both directions) |
| **offline** | `randomness`, `matrix_products`, `triple_products` (OT products), `authenticate` (MAC OT products), `assemble`, `sacrifice`, `random_bits`, `mac_check` |
| **online** | `input`, `open_w`, `forward_local`, `activation_local`, `activation_open`, `activation_chains`, `open_e`, `backward_local`, `output`, `mac_check` |

Per phase: **wall** time, **cpu** time (the whole process, all threads, so cpu ≈ cores × wall for a parallel phase),
bytes **sent** per direction (main channel + all OT channels, payload only), **flights**, and random OTs consumed.
A *flight* is a maximal run of messages in one direction on a channel and a round trip is 2 flights, as in the sibling
baselines. The **SUMMARY** block at the end of the server's output gives, for client and server separately, the
computation (wall and cpu, offline and online), the communication between the two (per direction, offline and online)
and the rounds.

- **Online** rounds are on the main channel and are exactly `11·iters + 5` round trips (225 at the defaults; 221 with
  `--semi-honest`, which has no MAC check): 11 per iteration (table above), the input flight, the output opening and the
  4 round trips of the final MAC check. They do not depend on `d`.
- **Offline** rounds: the main-channel part (coin tosses, sacrifice and bit openings, MAC checks) is constant, and the OT
  channels run in parallel; `ot-fl` reports the flights of the busiest OT channel (an approximation of the critical path).
- Online *wall* time at each party includes waiting for the other; the cpu columns are the actual computation.
- CSV columns (`--csv`): `client_offline_*` = setup + offline, `client_online_*`, the same for the server,
  `comm_{offline,online}_{c2s,s2c}_bytes`, `rounds_online_roundtrips`, `rounds_offline_{main,ot}_roundtrips`, `ots`.

- The cost is in the **offline phase**, as in the paper. Malicious security makes it about 5 to 6 times as expensive at
  small `d` (authentication and the sacrifice partner roughly double the OT products and add one OT product per value for
  the MACs) and about 4 times at `d = 1000`; the online phase costs the same in both modes except for the MAC check
  (4 round trips) and the 16-byte MACs that double the openings.
- Offline traffic is dominated by the OT-product corrections: 127 field elements per product. At small `d` it is the
  activation gadget (about 26,000 scalar triples and 7,200 random bits for 80 samples); from `d ≈ 100` the matrix
  products and the authentication of the client's masks (`U`, `Uh`: `2·n·d` values) take over. The traffic is
  asymmetric because the client is the message sender for the matrix products and the masks.
- The online phase is 11 round trips per iteration regardless of `d`. On loopback it takes about 0.8 ms per iteration
  at small `d`; over a real link it is dominated by the 225 round trips.
